# Разработка и проверки качества

Проект использует Java 21 и Maven 3.9. Общий `pom.xml` содержит версии и правила
для обоих сервисов. Сервисы остаются отдельными приложениями со своими БД и
Docker-образами. Каталог `transfer_service` пока сохраняет прежнее имя, чтобы
не ломать существующие команды и ссылки.

## Команды из корня репозитория

```powershell
# Если по умолчанию установлен другой JDK:
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-21'
$env:Path = "$env:JAVA_HOME\bin;$env:Path"

.\mvnw.cmd spotless:apply          # исправить форматирование
.\mvnw.cmd verify                  # формат, линтинг, unit- и архитектурные тесты
.\mvnw.cmd verify -Pintegration    # дополнительно PostgreSQL Testcontainers; нужен Docker
.\mvnw.cmd -pl account-service verify -Pintegration
.\mvnw.cmd -pl transfer_service verify -Pintegration
```

На Linux/macOS: `bash mvnw` вместо `.\mvnw.cmd`. Enforcer отклоняет неподдерживаемый
JDK, Maven и дубли зависимостей. `verify` сам не меняет файлы: форматирование
исправляется отдельной командой. Интеграционные тесты имеют суффикс `IT` и
запускаются Failsafe только в профиле `integration`; CI всегда включает этот профиль.
Отсутствие Docker не превращается в молчаливый пропуск интеграционных тестов.

Spotless использует Google Java Format в стиле AOSP: четыре пробела, единый порядок
импортов и удаление неиспользуемых импортов. POM-файлы форматирует SortPom.
Для YAML, properties и документации проверяются завершающий перевод строки и
пробелы в конце строк. Checkstyle проверяет конструкции Java, wildcard-импорты,
пустые catch-блоки, фигурные скобки и запрещает `System.out`, `System.err` и
`printStackTrace`. Конфигурация находится в `config/checkstyle.xml`.

Docker-сборки запускаются из корня, например:

```powershell
docker build -f account-service/Dockerfile -t account-service .
docker compose up --build
```

Образы собираются с общим parent POM и проверками формата/линтинга; тесты выполняет
CI. Сборочный контекст исключает `.env`, `.git`, Maven-кэш и `target`.

## Границы слоёв

- `controller`: HTTP-маршруты, валидация входных DTO и статусы ответов.
- `web`: обработчики HTTP-ошибок, формат ответа об ошибке и фильтр request ID.
- `service`: прикладные операции и транзакционные границы.
- `model`: сущности и бизнес-инварианты, без зависимостей от транспортных адаптеров.
- `repository`: работа с БД.
- `client`: HTTP-интеграция и перевод сетевых ошибок в свои исключения.
- `messaging`: адаптеры брокера, сообщения и конфигурация транспорта.
- `exception`: бизнес-исключения; HTTP-статусы определяет `web`.

ArchUnit закрепляет эти границы тестами. Контроллеры не должны работать с
репозиториями, сущностями или внешними клиентами напрямую. Open Session in View
отключён; чтение и изменения БД должны завершаться внутри сервисных транзакций.
Request DTO не создаются из сущностей. Response DTO пока используют небольшие
`fromEntity`-фабрики; отдельная библиотека маппинга здесь не нужна.

## Ошибки, деньги и логирование

Ошибки HTTP сохраняют контракт `timestamp`, `message`, `error`, `path`, `status`.
В transfer-service сохранено необязательное поле `transferId`. Невалидный JSON,
неправильный UUID и Bean Validation возвращают `400`; отсутствующий ресурс —
`404`; конфликт версии — `409`; недостаток средств — `422`. Неожиданный сбой
возвращает нейтральный `500`. Ошибки Spring MVC, включая `405` и `415`, сохраняют
свои статусы и заголовки. SQL, stack trace и rejected values не попадают в ответ.

Ошибки соединения с account-service возвращаются как `503`, неверный ответ
внешнего сервиса — как `502`. Исходная причина сохраняется в исключении для
диагностики; пустой успешный ответ считается ошибкой интеграции.

`X-Request-ID` возвращается в HTTP-заголовке и добавляется в MDC. Входной ID
принимается только при безопасном формате и длине до 64 символов; иначе создаётся
UUID. Контекст очищается даже при исключении. Обработчики сообщений используют
`transferId` и `eventId`. В логах нет полных сообщений с суммами и счетами.
Ожидаемые отказы и дубликаты не логируются как неожиданные системные ошибки.

Финансовые изменения и отметка обработки `transferId` выполняются в одной
транзакции. Дедуп использует PostgreSQL `INSERT ... ON CONFLICT DO NOTHING`:
JPA `save` с назначенным UUID может выполнить `merge` и не обеспечивает дедуп.
Тесты проверяют повторную и параллельную доставку, а также откат отметки вместе
с операцией. Идемпотентность требует внешней транзакции (`MANDATORY`).

Перевод на тот же счёт и между разными валютами отклоняется. В HTTP DTO проверяются
неотрицательный начальный баланс, положительная сумма и точность `numeric(19,4)`.
Конечный статус перевода не меняется при повторном событии; `@Version` защищает
от конкурентной перезаписи. Технический сбой обработчика не превращается в
бизнес-результат `FAILED`, а пробрасывается инфраструктуре доставки.

## Что ещё нужно до реального production

Это базовые инженерные проверки, а не подтверждение готовности системы к работе
с реальными деньгами. Следующие задачи требуют отдельного изменения и проверки:

1. **Outbox и восстановление доставки.** Запись в БД и публикация события пока не
   атомарны. Нужны outbox, publisher confirms и reconciliation зависших `PENDING`.
2. **Политика повторов и DLQ/DLT.** Нужны ограниченные попытки, backoff и сохранение
   проблемных сообщений. Без этого проброшенная техническая ошибка сама по себе
   не гарантирует корректное восстановление. Настройки зависят от текущей миграции брокера.
3. **Хранение результата обработки.** Сейчас дедуп фиксирует успешное движение денег.
   Для детерминированного replay нужно сохранять также исходный отказ и payload/hash
   запроса, чтобы один `transferId` не мог использоваться с другими реквизитами.
4. **Миграции БД.** `ddl-auto=update` остаётся dev-настройкой. Перед развёртыванием
   нужны Flyway/Liquibase, явная миграция нового поля `transfer.version` и
   `ddl-auto=validate` для production. Автоматический baseline существующих БД не включён.
5. **HTTP-идемпотентность.** Дедуп событий не защищает от двух отдельных POST-запросов
   клиента. Нужен API-контракт с `Idempotency-Key`.
6. **Валюты и эксплуатация.** Общую сумму балансов нельзя считать финансовым итогом
   разных валют без группировки/конвертации. Также нужны аутентификация/авторизация,
   метрики, health/readiness, tracing и нагрузочные проверки.

Исторические заметки в `review/` и старые ручные сценарии описывают предыдущие
этапы. Для процесса разработки и актуальных quality gates используй этот документ.
